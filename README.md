## 运行验证

```bash
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./build/rank_demo.exe
```

8 个用户同时对同一个物品反复购买和回退，每人 40 次操作，每做完一次就查一次排行榜。
三类事件按发生顺序写进 `demo_data/demo.log`，行首是从开跑算起的毫秒数：

| 事件 | 记的是什么 |
|---|---|
| 操作 | 谁、什么时候、买还是退、哪个订单、引擎返回什么、真实净次数变成多少 |
| 查询 | 这一刻榜单的版本号和内容，以及比真实数据落后多少 |
| 更新 | 榜单换版本了，把换版本前后的真实数据和榜单并排列出来 |

「真实净次数」是 demo 自己数的（买成功 +1，退成功 −1），代表业务上到底卖了多少；
「榜单」是引擎对外发布的快照。两者的差就是榜单更新的延迟。

一次实跑（8 用户 × 40 次操作，榜单最多 50 ms 更新一次）：

```
[   354.301] 查询  版本=6    榜单: 物品42=47                真实净次数=60       榜单落后 13
[   369.770] 操作  用户3   购买 订单=4000022    +1 件  -> ALREADY_PURCHASED  真实净次数=60
[   369.782] 操作  用户2   购买 订单=3000023    +1 件  -> OK                 真实净次数=61
[   369.794] 查询  版本=7    榜单: 物品42=60                真实净次数=61       榜单落后 1
[   369.797] 更新  榜单版本 6 -> 7（上面这次查询发现的）
                   更新前  真实净次数=60       榜单: 物品42=47                落后 13
                   更新后  真实净次数=61       榜单: 物品42=60                落后 1
                   这一版之内落盘 22 笔操作，只往榜单上改了 1 个条目；ts_merged 1791965718796453000 -> 1791965718858653000
```

两处看着别扭但都是对的：

- **相邻几条「操作」的真实净次数不一定递增**。8 个线程在同时加减，每条打的是*这次操作自己做完之后*的那个值（从原子加的返回值算出来），而写日志的先后和加减的先后本来就是两回事。
- **偶尔会出现「榜单超前」**。demo 是在调用返回之后才加自己那个计数的，引擎在返回之前就已经把这笔算进去了，所以有那么一小会儿榜单上的数反而更多。这一跑里最多超前 2。

日志共 714 行，11 次更新事件。跑完的汇总：

```
用户数 8，每人 40 次操作，一共调了 320 次，耗时 632.5 ms
  购买成功 176，回退成功 55
  被判重挡下：重复购买 36，重复回退 42；订单不存在 11；其他 0
排行榜查询 320 次，其中 10 次发现榜单换了版本
已落盘操作 231 笔 -> 应用到榜单 11 个条目，合并比 0.0476
最后对一遍账（三个数来自三条不同的路）：
  demo 自己数的真实净次数     物品42 = 121
  引擎订单表求和              物品42 = 121
  强制更新之后的榜单          物品42 = 121
  -> 三个数一致
```

日志里能直接看到的几件事：

| 现象 | 日志里的样子 |
|---|---|
| 买退折成加减 | 同一个物品，购买记 `+1`、回退记 `−1`，榜单上就是两者相抵之后的净次数 |
| 重复提交挡得住 | 320 次调用里 89 次被挡（`ALREADY_PURCHASED` / `ALREADY_REFUNDED` / `ORDER_NOT_FOUND`），真实净次数一动不动 |
| 判重发生在写文件之前 | 被挡的 89 次没进 `ops.log`，文件里正好 231 条 = 176 买 + 55 退 |
| 榜单更新有延迟 | 「查询」行的「榜单落后」多数时候不是 0，最多一次落后 18 |
| 一版之内的操作会合并 | 上面那次更新吃掉 22 笔落盘操作，榜单上只改 1 个条目 |
| 延迟是有上限的 | 633 ms 跑出 11 次更新，和「最多 50 ms 更新一次」对得上 |
| 数对得上 | 最后三条独立的路算出同一个数 121 |

数据文件可以使用tool里的工具查询校验：

```bash
./build/rank_check.exe demo_data --dump --nonzero
```

```
== ops.log ==
  记录数      : 231  (购买 176 / 回退 55)
  ts 严格递增 : 是
== rank.dat ==
  长度        : 32 字节 (期望 16 + 16 × 1 = 32) -> 有效
  ts > ts_merged 的记录 : 0 条（这些是还没算进 rank.dat 的）
  rank.dat 的计数 == ops.log 中 ts <= ts_merged 的 delta 之和 : 是
== 按 ops.log 算出来的全量计数 ==
  42 121
```

参数可调，全部见 `rank_demo --help`，常用的几个：

| 选项 | 默认 | 说明 |
|---|---|---|
| `--users <a>` | 8 | 同时操作的用户数 |
| `--ops <n>` | 40 | 每个用户做多少次操作 |
| `--item <id>` | 42 | 所有用户都操作这一个物品 |
| `--refund-pct <p>` | 35 | 回退占比 |
| `--think-ms <n>` | 10 | 两次操作之间歇多久 |
| `--tmax <ms>` | 50 | 榜单最多多久更新一次，调小了更新更频繁、落后更少 |
| `--dir <目录>` | demo_data | 数据目录，跑之前会清空 |

## 项目结构分析

```
include/rank/   对外头文件：config.h  types.h  engine.h  metrics.h
src/            引擎本体，8 个 .cpp
tests/          6 个用例文件，按模块分
bench/          并发压测入口
tools/          并发演示 + 对账工具 + 崩溃注入
docs/           需求、设计、测试计划、测试结果、构建说明、开发记录
prompt/         给 ai 的提示词
rank_proj.md    最初的业务场景问题
```

代码 4359 行（不含自带的 GoogleTest 精简版），其中引擎本体 1050 行、对外头文件 182 行、测试 1506 行。

五个产物：

| 产物 | 干什么 |
|---|---|
| `build/rank_demo.exe` | 演示程序，多个用户同时对同一个物品反复买退，按事件类型记日志，给人看的 |
| `build/tests/rank_tests.exe` | 全部自动化用例，按照ai给出的测试设计跑测试 |
| `build/rank_bench.exe` | 并发压测入口，同样是按照ai给出的压测设计跑压测 |
| `build/rank_check.exe` | 对账工具，直接按字节读两个数据文件（一个操作记录文件，一个排行榜数据文件，读出来看按照操作之后排行榜数据是否正确，是字节文件，需要用脚本可视化出来） |
| `build/rank_crash_helper.exe` | 崩溃注入，跑到指定位置直接终止进程（ai给出宕机恢复的测试设计，在不同节点崩溃之后重启看是否正常恢复） |
