dp-workflow 开发工作流

dp-workflow（编排）→ dpwf-req → dpwf-dev → (dpwf-comment ∥ dpwf-review) → done · 状态机驱动 · 门禁向前 / 分级回退

skill 编排（dp-workflow + 四阶段）

dp-workflow 编排 — 读状态 → 路由到对应阶段 skill dpwf-req 需求 — 出需求文档（唯一 owner，版本化） dpwf-dev 开发 — 讨论需求 → 设计 → 实现 → 测试（loop） dpwf-comment 注释 — 实现定稿后审查/补全注释 dpwf-review 审查 — 实现定稿后对照需求 + 设计审查

门禁（向前）与回退（分级）

门禁：requirements_approved → design_approved → implementation_complete → tests_passed → review_approved
回退：impl_bug → 实现 design_gap → 设计 spec_gap → 需求 new_feature → 需求 review_feedback → 按意见回对应层

会话交接（多窗口协作）

每个 skill 可跑在独立的 Claude 窗口，上下文不共享，靠文档交接。未交接 = 未完成——窗口结束但没更新状态 / 文档，状态机就停在半路。

窗口启动（读盘）
1. 读 docs/dp-workflow/STATE.md → 看 current_state，判断本窗口跑哪个 skill。
2. 读上一环节拥有的文档。
3. 按 .claude/skills/ 里该 skill 的定义执行。
窗口结束（落盘，才叫交接）
1. 更新自己拥有的文档 + 变更记录（版本 +1）。
2. 更新 docs/dp-workflow/STATE.md 的 current_state。
3. 只在门禁事件时交接；内环 impl_bug 留在同一窗口。
拆法安全说明
skill 之间（门禁处）✅ 安全文档边界清晰，读上一份文档即可续
dpwf-dev 内部「设计 → 实现」⚠️ 谨慎实现依赖"为什么这么设计"；要拆必须让 docs/dp-workflow/design/DESIGN.md 写够设计理由
dpwf-comment / dpwf-review✅ 天然并行两个独立窗口，各读代码 + 文档，产出各自反馈

五条修正规则

1
并行只在实现定稿后
dpwf-comment ∥ dpwf-review 互相并行，但都不与 dpwf-dev 并行。
2
注释是实现的验收标准
写代码的 agent 自己写注释，dpwf-comment 只审查。
3
需求单一 owner
dpwf-dev 不直接改需求，只提 spec_gap / new_feature 回 dpwf-req。
4
测试派生自验收标准
否则「测试出 bug → loop」无据可依。
5
上下文按模块拆分
单会话只做同一模块，避免上下文膨胀。
控制流定义见 .claude/skills/dp-workflow/templates/STATE.md · skill 约定见 .claude/skills/（dp-workflow + 四阶段）· 终止条件：验收标准全过 + review_approved，或预算耗尽
