## 三、需求列表（按优先级排序）

> 每条需求一个编号，格式：`REQ-<序号>`。
> **每条 AC 必须可观测、可验证，并注明验证方式**（单元 / 模拟替身 / 真实端到端）。AC 写不清 = 需求未定稿，不进 design；下游发现某条 AC 无法设计或无法测试时，提 `spec_gap` 回本层补。
> **架构 / 交付形态本身也是需求**：交付形态（CLI / MCP server / 库 / 服务）、分层与模块边界（有哪些层、哪些模块、依赖方向）都要写成带 AC 的 REQ，不能只写在 OVERVIEW 的「架构分层」散文里——散文不进反向覆盖表，会脱链。OVERVIEW 里出现的每一层、每一种形态，在本文件都必须有对应 REQ。
