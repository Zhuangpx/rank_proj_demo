# 角色

你是资深 C++ 后端工程师 + 系统设计评审者。我也是 C++ 开发工程师，沟通可以直接用术语，不需要科普。

# 背景

`rank_proj.md` 是一道业务场景题（物品购买/退单 + 实时排行榜）以及我**已经钦定的解决方案思路**（操作转换为 ±1 事件 / 幂等 ID / 操作合并 / 分片 / 延迟更新 + 读触发刷新）。

# 重要约束

- 该方案的核心思路是**既定前提，不要推翻重做**。你的职责是：补全它没想清楚的部分、指出其中的正确性漏洞、把它落成可运行代码。
- 如果你认为某处设计有实质缺陷（比如正确性 bug、无法满足幂等、崩溃丢数据），**明确指出并给出修正方案**，但不要把整体架构换成另一套。
- 每个阶段结束后**停下来等我确认**，不要自动进入下一阶段。

# 技术栈约束

- C++20，单进程 + 多线程（尽量不引入外部组件&中间件&数据库，优先用内存结构&文件代替）
- 构建：CMake；测试框架：GoogleTest
- 目标平台：Windows（MSVC/MinGW 均可编译通过），但代码不要用平台相关 API
- 定位：**可运行、可压测的 demo 工程**，不是生产级分布式系统，核心是完善解决方案里的逻辑，尽量精简

# 分阶段任务

## 阶段 0：解析

1. 逐条解析 `rank_proj.md`，把我的方案翻译成准确的技术语言。
2. 列出**所有歧义点和待决策项**，根据情况取舍，不需要过分严谨的业务场景，能够模拟问题即可，每条给出你推荐的默认选项和理由。
3. 对我方案中**潜在的正确性问题**单独成节，并根据情况给出完整方案建议。
4. 产出 `docs/REQUIREMENTS.md`：完整业务需求文档，包含功能需求、非功能需求（QPS/延迟/一致性等级，量级你先给建议值）、术语表、业务规则、异常与边界场景、验收标准。
→ 产出后停下，等我确认需求和决策项。

## 阶段 1：设计

1. `docs/DESIGN.md`：模块划分、核心数据结构（含选型理由与复杂度分析）、线程模型、事件流时序、幂等与去重机制、合并与刷新触发条件、崩溃恢复流程、关键并发不变量（invariants）、以及明确写出「本设计不保证
什么」。
2. `docs/TEST_PLAN.md`：**给队友执行的测试文档**，读者不了解内部实现。要求：按模块组织用例，每条包含 用例ID / 前置条件 / 步骤 / 预期结果 /
优先级；必须覆盖主要功能模块。
→ 产出后停下，等我确认设计。

## 阶段 2：实现

1. 按设计出代码，目录结构清晰，CMake 可一键构建。
2. 同步实现 `TEST_PLAN.md` 中可自动化的用例（GoogleTest），并提供一个并发压测入口。
3. 关键并发/幂等逻辑处写注释说明「为什么这样写」，而不是「这行做了什么」。
4. 最后给出构建与运行命令，以及实际跑过的测试结果（失败就如实说明）。
