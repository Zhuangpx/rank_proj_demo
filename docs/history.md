# history

记录使用claude进行vibe coding过程中，一些比较重要的过程。

开发的主要思路是，先口语化最初的问题，然后初始化一段开始的提示词（init.md），交给ai润色，之后提交给claude。
init.md本身对开发钦定三步走，即需求完善-方案设计-代码实现和测试，每一步独立。
对于ai所给的输出，首先自己有一定的预期，参考ai输出的整体思路，具体每一小部分（比如数据结构如何设计等）根据自己的想法，再重构一套提示词给到claude。
这里有一个自己的小技巧，先让ai对详细输出，比如为什么这么设计，思考过程，在review完觉得没大问题之后，再让ai进行精简。

一开始尝试用dp-workflow跑一遍，发现场景太复杂，工程太大，时间成本太高。
所以按照上述思路重新跑一遍，简化问题。

除开要模拟问题和解决方案本身，场景设计和完善比较开放性，需要花费一定的时间在后者上面（实际开发中这部分反而是比较头大的...）。
在走完主体流程之后，反思得到一个问题：第一步的需求完善，应该不包含解决方案本身，而是仅仅描述需求比较合理（和当时二面面试官说的一致，描述需求本身，而不是人为确定任务）。第二步的方案设计，再让ai在自己预期的解决方案基础上进行方案设计。

演示思路：
1. 构建并启动项目
1. 模拟同时a个用户进行对同一个item_id进行频繁的购买&回退操作。
2. 每次有操作后都进行一次排行榜查询。
3. 按照事件类型记录日志文件：
  时间戳 购买回退操作，实际数据结果
  时间戳 排行榜查询结果
  时间戳 排行榜更新事件，更新前的数据&排行榜和更新后的数据&排行榜对比

使用agent：claude
使用模型：opus-5

开发用时：

0. 初始化

新建git仓库托管github，导入了一些skill。
`rank_proj.md` 准备好问题和场景描述。

1. 项目启动

`prompt\init.md` 准备好项目开始的提示词，整理成文档，交给claude优化描述。

2. REQUIREMENTS

对step0产出的REQUIREMENTS.md进行review，有修改意见提交给claude。

- 排行榜查询简单top即可

ai给出了很复杂的排行榜查询场景，纠正成了简单的topk查询。

- 完善刷新与合并的描述

这块描述非常模糊，要去ai完善描述。

- 数据持久化与恢复

claude设计的数据流过于复杂，考虑自己思考方案。
给到claude的修改意见是，模拟数据写入写出的主要功能，简化业务场景。

大体提示词：用文件模拟数据库（排行榜数据和操作数据），用内存模拟合并带更新的操作即可。维护排行榜上一次合并的时间戳和操作数据的时间戳，操作数据里的条目，只要操作的时间戳小于排行榜上一次合并的时间戳，就说明该操作已生效，用这种方式解决宕机重启的数据恢复。

- 验收

对于一些边界问题，让ai介入考虑更高效，因此验收交给ai来做。
性能上的验收，也由ai拟定一套标准。

3. design

预期是让ai出一份design和test_plan，即测试方案和设计方案一起出。

- 线程模型

考虑线程模型，从需求出发分析有什么行为。

```
业务
- 购买和回退行为
排行榜
- 排行榜读取行为
- 持久化记录
- 更新排行榜
```

让ai根据这些逻辑设计线程模型。

让ai按照这种方式推导，逻辑比原本直接设计线程模型的输出要清晰。
在review完没问题后，再重新让ai简化。

- 数据结构

提供一些预期的设计，作为提示词给ai润色。

```
- 订单
业务订单（购买与回退）
首先需要用（order_id，item_id，qty）维护一次订单操作，同一个order_id最多只能有一个1表示购买的qty和一个-1表示回退的qty。
正常业务一次购买应该有订单号，能够唯一索引和判断幂等。这里在内存空间里维护全量的订单号，模拟正常业务场景下的订单号唯一。需要加锁保证并发。

- 操作记录与提交队列
一次从业务过来的操作，对应一次+1/-1。
设计(order_id,item_id,+1/-1,time)，从业务过来的操作记录，写入操作记录数据，模拟正常业务场景的订单记录。
用一个队列维护多个这样的操作记录，一个线程处理写入事件。

- 待更新操作
针对同一个item的操作，进行合并（无序）在内存里，再批量写。
设计[item_id]->delta，每个item待更新的操作合集，每次有新的操作记录应该维护增加，每次批量更新完排行榜应该重置。
last_time上次把批量操作更新进排行榜数据的时间戳，操作记录的持久化文件里时间戳大于该时间的是还没更新排行榜的，每次更新排行榜取当前时间戳更新last_time进内存和持久化数据文件。

- 排行榜快照
启动时初始化的排行榜数据快照，读请求来时取出，需要记录加载时对应排行榜数据的时间戳，能说明非实时数据。
有更新操作时，同时更新快照。因此快照和实际排行榜数据是有延迟的，和更新排行榜操作是同步的。
```

之后再让ai进行整体逻辑的总结和画时序图。

测试文档主要靠ai输出，这一块自己基本上没有做出预期设计，交给ai的理由是测试设计成本高，且重复性工作比较高，ai来做会比较高效。
