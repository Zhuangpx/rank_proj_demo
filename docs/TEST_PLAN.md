# 实时排行榜 测试计划

> 阶段 1 产出。本文档给执行测试的人看，不要求了解引擎内部实现，只通过对外接口、配置项、两个数据文件和指标来判断对错。
> 需求见 `docs/REQUIREMENTS.md`。

---

## 1. 被测对象与可观测面

引擎是一个进程内的静态库，对外只有三个接口：

| 接口 | 说明 |
|---|---|
| `Purchase(order_id, uid, item_id, qty)` | 下单。返回 `OK / ALREADY_PURCHASED / INVALID_ARG` 或失败码 |
| `Refund(order_id)` | 退单。返回 `OK / ALREADY_REFUNDED / ORDER_NOT_FOUND` |
| `TopK(k, consistency)` | 取前 k 名，返回 `(item_id, count)` 列表、一个版本号、一个时间戳 `ts_merged`（这份榜单更新到什么时候）。`consistency` 取 `Stale`（默认）或 `Fresh` |

返回 `OK` 或 `ALREADY_*` 都算业务成功；只有返回 `OK` 才表示这次操作已经写进文件。

除接口外还有三样东西可以看：

- **两个数据文件**
  - `ops.log`：操作流水，只追加，不会被删。**每条记录定长 32 字节**，内容是 `(ts, order_id, item_id, delta)`，`delta` 为正表示购买、为负表示回退。文件长度必然是 32 的整数倍。
  - `rank.dat`：榜单文件，可以手动删掉或改坏。内容是 `[ts_merged | 条目数 | (item_id, count) × N]`，**长度必然等于 `16 + 16 × 条目数`**。
- **指标**：刷新次数、刷新耗时、合并比、当前陈旧度、累计 delta 总和。合并比 = 应用到榜单的事件数 ÷ 提交的操作数，越小说明合并效果越好。
- **压测入口**（`bench`）：可配线程数、操作总数、读写比、退单比例、物品数、热点集中程度（Zipf α）、随机种子。同一个种子跑两遍结果必须一样。

## 2. 测试环境与通用前置

- 构建：`cmake -B build && cmake --build build`，MSVC 与 MinGW 各跑一遍。
- 每个用例在**干净的数据目录**里跑：目录存在、里面没有 `ops.log` 和 `rank.dat`。除非用例另有说明。
- 默认参数（可通过配置结构覆盖，用例会写明改了哪个）：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `T_max` | 200 ms | 最长多久自动刷新一次 |
| `T_min` | 10 ms | 两次由 `Fresh` 读触发的刷新之间，至少隔多久 |
| `N_pending_max` | 10000 | 攒够这么多个待刷新物品就刷一次 |
| `K_max` | 1000 | `TopK` 允许的最大 k |
| 合批窗口 / 批大小 | 0 / 4096 条 | 攒够任一条件就落一次盘。窗口默认 0 = 不等：队列里有什么就写什么，这一批写盘期间新来的操作堆成下一批，批量随压力自己长大。在 Windows 上把它设成几毫秒反而会掉吞吐，见 §9 |
| `rank.dat` 落盘周期 | 1 s | |
| 分片数 | 订单 64 / 物品 8 | |
| 提交队列上限 | 64K 条 | 积压到这个数，提交方会被挡住等待 |

- **崩溃注入**：配置里可以指定一个崩溃点，引擎跑到那里会立刻终止进程（不做任何收尾）。可选位置：`写 ops.log 之前` / `fsync 之后返回之前` / `刷新中途` / `写完 .tmp 还没改名`。
- **对账工具**（`rank_check`）：独立于引擎实现，直接读 `ops.log`，每 32 字节一条，把 `delta` 按 `item_id` 全部加起来，输出 `(item_id, count)` 全量列表。多个用例的「与对账工具一致」就是指跑它再逐项比对。

## 3. 优先级

| 级别 | 含义 |
|---|---|
| P0 | 正确性，必须全过，有一条不过就不能进入下一阶段 |
| P1 | 行为符合设计，允许先记缺陷再修 |
| P2 | 性能与观测，只要求跑出数据并记录 |

「自动化」列：`是` = 阶段 2 要写成 GoogleTest 用例；`半` = 自动跑但结果要人看；`否` = 手工执行。

| 用例ID | 前置条件 | 步骤 | 预期结果 | 优先级 | 自动化 |
|---|---|---|---|---|---|
| C-01 | `T_max` 设为 50 ms，不发任何读请求 | ① 提交 1 笔购买 ② 什么都不做，等 200 ms ③ `TopK(10, Stale)` | 不读也会刷新，这笔购买已经体现在榜上 | P0 | 是 |
| C-02 | `T_max` 默认 200 ms | ① 高速写 1 秒 ② 停止写入 ③ 等 `T_max` ④ `TopK(全部, Stale)` 与对账工具比对 | 停写 `T_max` 之后，`Stale` 读的结果就等于真值 | P0 | 是 |
| C-03 | `T_min` 设为 50 ms，`T_max` 设为 60 s | **8 个读线程**在 2 秒内尽可能多地发 `TopK(10, Fresh)`，记录读次数与刷新次数 | 刷新次数约等于 2 s ÷ 50 ms = 40 次量级，远小于读次数。若两者接近，说明最小间隔没生效。这里不能用单线程：单线程串行读时每次读都是「等满 `T_min`、刷一次、返回」，读次数天生等于刷新次数，测不出东西；最小间隔真正省掉的是同一窗口里多个读请求各刷一次 | P0 | 是 |

## 11. 自动化落地情况（阶段 2 填写）

自动化用例全部在 `tests/` 下，一个可执行文件 `rank_tests`，按模块分文件。GoogleTest 的三级来源见 `tests/CMakeLists.txt`。

| 模块 | 用例文件 | 已自动化 | 没自动化的 |
|---|---|---|---|
| A | `test_a_submit.cpp` | A-01~A-13（A-04/A-05/A-07 合成一条链式用例） | — |
| B | `test_b_query.cpp` | B-01~B-12 | — |
| C | `test_c_flush.cpp` | C-01~C-06、C-09、C-10 | C-07、C-08（要跑多轮压测看趋势） |
| D | `test_d_persist.cpp` | D-01~D-11（D-01 与 D-02 合成一条） | D-12（要准备百万级 `ops.log`） |
| E | `test_e_concurrency.cpp` | E-01、E-02、E-03、E-05 | E-04、E-06（分钟级 / 要人为制造写失败）；E-07 的做法是 `rank_tests --gtest_repeat=N`，不单独写用例 |
| F | `test_f_config.cpp` | F-01~F-06 | F-07、F-08 |

规模上的取舍：E-01 计划里写的是 100 万笔，用例里跑的是 32 线程 × 5000 笔。理由是整套用例要能在改一行代码后随手跑一遍，百万级那一档交给压测入口。同理 F-02 跑 5000 笔而不是 10 万笔。

F-08 只做了一半：这台机器上没装 MSVC（`cl.exe`、`vswhere.exe`、Visual Studio 目录都没有），只能用 MinGW（GCC 15.2.0）这一边验证，开 `-Wall -Wextra` 零警告。MSVC 那一边**没有实测过**。代码里唯一的平台分支在 `src/util.cpp` 的 `SyncFile()`：Windows 走 `<io.h>` 的 `_commit`，其他平台走 `<unistd.h>` 的 `fsync`——标准库里没有把文件刷到盘上的接口，这一处躲不掉。

每一版实际跑出来的结果记在 `TEST_RESULTS.md`，包括半自动用例的完整命令和数字。本文件只写「要测什么、判据是什么」，不记具体数值。

## 12. 缺陷记录要求

一条用例不过，记录时必须带上：用例 ID、完整配置参数、随机种子、`ops.log` 和 `rank.dat`（能留就留一份）、实际输出与期望输出的差异明细。并发和崩溃类问题没有这些就没法复现。
